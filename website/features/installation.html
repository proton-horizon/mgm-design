MGM Design / Guide

One site, its own workspace.

Each Cloudflare installation uses a dedicated Worker, D1 database, and private R2 bucket. It can use a custom domain or its matching workers.dev hostname. The viewer and protected mocks share that one hostname.

Deploy

Follow the README setup commands. Configure the instance's Worker name, database name and ID, bucket name, site URL and display name using your existing environment conventions. The project that owns this installation also owns its settings, deployment workflow, and credentials. Set SETUP_SECRET as a Worker secret. Keep customer configuration and credentials out of the shared MGM repository.

Give the deployment script --output <path> to generate configuration in the owning project. Relative paths start from the directory where you run the command. Ignore that generated file and private files in the owning project's Git configuration. The script points back to the MGM source checkout, checks the Worker build, applies database migrations, and deploys. A failed step stops the remaining sequence. Keep the same database and bucket when updating.

After deploying, verify first-time setup and sign-in on the actual site. Password hashing uses the Worker's native runtime and must fit the installation's CPU limit; local tests cannot establish that limit. The generated configuration enables the required Node.js compatibility setting.

Follow main automatically

Each installation configures its own update pipeline and credentials. That pipeline fetches MGM Design's main branch, installs dependencies, builds the framework, and deploys using the installation's settings and output path. A direct Cloudflare Builds checkout of MGM Design can use the script's default output location, with settings held in the Worker's build configuration. See the README for command and build-identifier details.

Move to a custom hostname

Keep the Worker, database, and bucket. Change the configured site URL and attach the custom domain. Users sign in again on the new hostname; source publishers must use the new destination URL. Stored users and designs remain in the same database and bucket.

How it works

The framework build updates application code and assets. Mock publication is a separate API operation. Database migrations must remain compatible with the running code; back up persistent data before changing schema. A daily cleanup removes expired sessions, preview grants, and obsolete stored files.

The setup script and configuration isolation are tested locally. Automatic upstream updates through a separate owning repository, a live two-installation rollout, and independently owned Cloudflare-account onboarding still need validation.
