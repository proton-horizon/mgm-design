MGM Design / Guide

One site, its own workspace.

Each Cloudflare installation uses a dedicated Worker, D1 database, and private R2 bucket. It can use a custom domain or its matching workers.dev hostname. The viewer and protected mocks share that one hostname.

Why one Worker per site?

A Worker runs the viewer, sign-in, administration, and publishing API. Its D1 database holds accounts, sessions, projects, and publication records. Its private R2 bucket holds the mock files. Adding another project to the sidebar uses this same installation; it does not need another Worker.

A separate client or design collection gets its own installation and resources when needed. A single design site needs only one installation. Each site can continue operating under its owner's control.

Two independent update flows

Update MGM Design

Push framework code to MGM's main branch. Each connected installation's Cloudflare Builds pipeline checks and deploys that code using its own settings. Accounts, projects, and stored mocks stay in that site's database and bucket.

Publish an app's designs

Push mocks in the app repository's design/ directory to its main branch. That repository's GitHub Actions job sends the bundle to MGM's publishing API. It uses a project publishing token and does not redeploy the viewer.

A failed mock job does not block the app's production deployment. Each destination has its own URL and publishing token, so an app can publish to several sites independently. See Publish designs for the source-repository setup.

Deploy

Follow the README setup commands. Configure the instance's Worker name, database name and ID, bucket name, site URL and display name using your existing environment conventions. The project that owns this installation also owns its settings, deployment workflow, and credentials. Set SETUP_SECRET as a Worker secret. Keep customer configuration and credentials out of the shared MGM repository.

Give the deployment script --output <path> to generate configuration in the owning project. Relative paths start from the directory where you run the command. Ignore that generated file and private files in the owning project's Git configuration. The script points back to the MGM source checkout, checks the Worker build, applies database migrations, and deploys. A failed step stops the remaining sequence. Keep the same database and bucket when updating.

After deploying, verify first-time setup and sign-in on the actual site. Password hashing uses the Worker's native runtime and must fit the installation's CPU limit; local tests cannot establish that limit. The generated configuration enables the required Node.js compatibility setting.

Follow main automatically

In each Worker's Cloudflare Builds settings, connect MGM Design's main branch and configure that installation's build token, variables, and commands. Keep those settings synchronized with the project that owns the installation. Pushes to main then rebuild the framework with the site's own database and bucket. No consumer version edits or private owner-repository checkout are needed. See the README for exact build settings and commands.

  1. In GitHub's installed Cloudflare Workers and Pages app settings, authorize the MGM repository. When using selected repositories, add MGM and keep existing selections. A successful clone of a public repository does not establish permission to receive pushes.
  2. Connect the shared MGM repository to the installation's existing Worker.
  3. Select main as the production branch and disable preview deployments.
  4. Choose that installation's deployment token. Copy its account, Worker, database, bucket, site URL, and display name into the build environment.
  5. Copy the Node/pnpm versions, build command, and guarded deployment command from the README. Enable the build trigger.
  6. Verify a main push produces a successful build and the expected framework commit at the site, then confirm existing accounts and designs still work.

Only one deployment may run at a time for an installation. The deployment command checks the current main commit and skips outdated builds. That check does not replace serialization: an older deployment already in progress must finish before another starts. If setup relies on an account-wide build limit of one, check that limit before enabling updates and before increasing build concurrency.

Credentials and MCP

Deployment tokens belong in Cloudflare Builds. Project publishing tokens belong in the source app's existing secret storage. The first-admin setup secret belongs on the Worker. None of these credentials belongs in a published mock or the shared MGM repository.

Cloudflare Builds currently uses user-owned API tokens. The README lists the permissions needed for this deployment. They cover resources within an account or zone, not just one named Worker. Separate tokens let an owner revoke each installation's automation independently, but do not isolate the tokens' access to resources within a shared account.

A connected Cloudflare MCP can help inspect resources and build results, configure build settings, and diagnose failures, provided its credential has the necessary permissions. Creating user tokens also requires token-management permission; use the owner's signed-in Cloudflare browser when the connected MCP credential does not have it. If an initial build connection fails through the API, complete it in the dashboard, then use MCP for deployment-token registration, build settings, and starting and inspecting builds. MCP access and the deployment token are separate credentials. Ordinary main-branch updates run in Cloudflare without an agent or browser session.

Move to a custom hostname

Keep the Worker, database, and bucket. Change the configured site URL and attach the custom domain. Users sign in again on the new hostname; source publishers must use the new destination URL. Stored users and designs remain in the same database and bucket.

Updates and recovery

The framework build updates application code and assets. Mock publication is a separate API operation. Database migrations must remain compatible with the running code; back up persistent data before changing schema. A daily cleanup removes expired sessions, preview grants, and obsolete stored files.

Instance variables alone do not enable updates. Each Worker needs an enabled Builds trigger and an authorized build token. Failed builds leave the current application running; inspect that Worker's build result in Cloudflare. A stopped or superseded build is separate from a source app's mock-publication result.

  • No framework build appeared: check the repository connection, main-branch trigger, and whether builds are enabled for that Worker. If Cloudflare says the project is disconnected from Git, check that the MGM repository is included in the Cloudflare GitHub app's authorized repositories.
  • Framework build failed: inspect its Cloudflare build log for the failing install, test, migration, or deployment step. Check token access and installation variables. Fix the cause and retry against current main; do not replace the database or bucket.
  • Mocks are older than expected: inspect the project's latest publication status and linked GitHub Actions run. A failed attempt leaves the last successful set visible. If the job never reached MGM, GitHub Actions contains the failure report.
