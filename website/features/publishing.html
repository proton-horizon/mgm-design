MGM Design / Guide

Keep designs with the app.

Mocks live under design/ in the source app repository. MGM Design receives browser-ready HTML, CSS, JavaScript, and runtime assets. Build source code and export models in the app repository first.

Connect a repository

  1. Register the project in the destination site's administration screen and store its token in your existing secrets system.
  2. Create design/manifest.json using the maintained bundle contract. Declare boards, screen entries and viewport sizes, and explicitly list all runtime files.
  3. Run the shared publisher from the app repository with its site URL, project ID, and token supplied through the environment.
  4. Add a separate workflow for pushes to main. Keep its outcome independent from the app's production deployment. 
MGM_SITE_URL=https://design.example.com MGM_PROJECT_ID=my-app \
  node /path/to/mgm-design/scripts/publish.mjs

Supply MGM_PUBLISH_TOKEN through existing secret wiring. These names are examples for mapping configuration, not a requirement to move or rename secrets. Multiple destinations need separate URLs and tokens with independent outcomes.

Preview while working locally

Run pnpm dev:mocks --directory ../my-app/design in MGM Design. Add another --directory for each app. Open the printed local URL; no sign-in or publishing token is needed. Valid changes reload automatically. Invalid changes keep the previous designs and report the problem in your terminal. This read-only workspace is temporary and does not change your hosted sites. Stop the command when finished.

When something goes wrong

The viewer keeps the last successful designs. Its publication indicator shows when a newer attempt failed or stopped reporting progress, with a link to the GitHub Actions run when provided. If the site was unreachable, GitHub Actions may be the only record of the failed attempt.

The publisher registers before reading and validating the bundle. To report an earlier compilation/export failure on the site, register an attempt through the API before that build and report its result. See the contract for the exact endpoints.

How it works

Only explicitly listed files are uploaded. The server validates the complete set, stores it under an isolated publication ID, then changes the visible pointer atomically. Old or failed uploads cannot replace a newer successful set. Publishing does not deploy the viewer or need Cloudflare account credentials.

Published files must exclude secrets, editable Blender masters, briefs, and build-only inputs. Bundle the runtime dependencies that the mock actually uses. Uploading a GLB or a JavaScript library does not by itself prove that its browser features work in the sandbox.
